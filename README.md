# Jam SMART on FHIR Platform

**v0.2.3** · Apache 2.0 · Java 21 · Spring Boot 3.3.5 · Spring Authorization Server 1.3.0

A production-ready, open-source **SMART on FHIR App Launch v2.2** authorization server and reference client for HAPI FHIR R4. Built as a Digital Public Good — free forever, no vendor lock-in, no SaaS dependency.

A project of the **[Dr. Akriti Jamwal Foundation](https://ajcommons.org/)** — a Section 8 not-for-profit registered in India (CIN U88900BR2026NPL086460), dedicated to open digital infrastructure for public health.

---

## Why this exists

SMART on FHIR is the open standard that lets clinical apps — EHR widgets, patient portals, research tools, mobile apps — securely launch inside a hospital system and receive a scoped FHIR access token tied to a real patient and encounter. Implementing it correctly requires more than just OAuth2: you need launch context, scope consent, PKCE for public clients, OIDC id tokens, and a JWKS endpoint that FHIR servers can use to verify tokens — all wired together correctly and securely.

**The gap in open source today:**

The existing landscape leaves health IT teams with poor choices:

| Option | Problem |
|---|---|
| **Keycloak** | General-purpose OAuth2/OIDC; the SMART on FHIR plugin was community-maintained, never completed EHR launch context binding, and is now effectively abandoned (last release 2022, open issues unresolved for 2+ years) |
| **HAPI FHIR's bundled auth** | Demonstration-quality only; not designed to be run standalone; no scope enforcement; no federated IdP |
| **Commercial EHR vendor auth** (Epic, Cerner) | Proprietary; impossible to self-host; SMART implementation is internal and non-portable |
| **Rolling your own with Spring Security** | Spring Authorization Server handles OAuth2 but has no knowledge of SMART — launch tokens, context binding, scope humanisation, PKCE enforcement, and the SMART discovery document all require significant custom work |
| **AWS Cognito / Azure AD B2C** | Cloud-only; large SaaS dependency; SMART scope semantics require custom Lambda/policy work; no EHR launch flow out of the box |

This project fills that gap: a **standalone, self-hosted SMART on FHIR authorization server** built on Spring Authorization Server 1.3.0, fully implementing SMART App Launch v2.2, production-audited, and designed to pair directly with HAPI FHIR JPA Server.

## What it implements

### SMART App Launch v2.2

- **EHR Launch** — the EHR (or any launch portal) generates a launch token bound to a patient and encounter, passes `?iss=&launch=` to the app, which then drives a full PKCE authorization code flow against this server
- **Standalone Launch** — app launches without EHR context; clinician picks a patient via the built-in patient picker before the authorization code is issued
- **Scope consent UI** — humanised scope descriptions (`patient/Patient.rs` → "Read your patient's demographics") on a Thymeleaf consent page; Spring AS stores consent decisions per app per clinician
- **PKCE (S256)** — enforced for all public clients; code verifier/challenge generated by the client and validated server-side; no `client_secret` required for public apps
- **SMART discovery** — `GET /.well-known/smart-configuration` returns authorization and token endpoints, supported scopes and capabilities, PKCE methods; proxied to the FHIR base URL via `SmartDiscoveryProxyFilter`
- **SMART token response** — `patient`, `encounter`, `need_patient_banner` returned as top-level JSON fields in the token response alongside `access_token`, exactly as required by the SMART spec
- **RS256 id_token** — signed with a per-deployment RSA keypair; JWKS endpoint at `/oauth2/jwks` for client-side and FHIR-server-side verification
- **SMART scope enforcement** — `SmartScopeAuthorizationInterceptor` rejects FHIR API requests whose token scope doesn't cover the requested resource and operation (e.g. `patient/Condition.r` rejects a `PUT`)
- **Token introspection** (RFC 7662) — `POST /oauth2/introspect` for FHIR servers to validate tokens on every request

### Security

- **Rate limiting** — `TokenEndpointRateLimitFilter`: token-bucket per IP on `/oauth2/token`, configurable burst/refill; protects against credential stuffing
- **Login lockout** — `LoginLockoutFilter` + `LoginAttemptService`: IP-based lockout after N failed attempts; Caffeine in-memory (single instance) with configurable window
- **XFF spoofing prevention** — `ForwardedHeaderFilter` registered at highest servlet precedence; all security filters read `getRemoteAddr()` only, never the raw `X-Forwarded-For` header
- **RSA key fail-fast** — server refuses to start in prod profile if no keystore is configured; no silent fallback to a generated key in production
- **Admin bootstrap** — first-run only; default admin credentials must be changed on first login; bootstrap is a one-time initialisation, not a backdoor
- **Role whitelist** — `AdminController` validates role against a hardcoded `{"CLINICIAN","ADMIN"}` set; no free-text role assignment
- **Launch token lifecycle** — single-use; session attribute cleared only after successful DB write; prevents replay

### Infrastructure

- **PostgreSQL** via JPA + Flyway schema migrations (dev: H2 in-memory, no migration needed)
- **Scheduled cleanup** — `TokenCleanupJob` nightly purges expired `oauth2_authorization` rows and orphaned consent records; Spring AS does not do this automatically
- **Federated identity** — `FederatedIdentityConfig` (active under `idp` profile) delegates clinician authentication to any upstream OIDC IdP (Epic, Azure AD, Okta, Keycloak); `PractitionerLookupService` resolves the clinician to a FHIR Practitioner resource and injects `fhirUser` into the id_token
- **CORS two-tier policy** — discovery and JWKS: any origin; token/revoke/introspect: configured allowed origins only

## Quick Start

```bash
git clone https://github.com/ajcommons/jam-smart-fhir-server
cd jam-smart-fhir
cp .env.example .env          # fill in ISSUER_URL, DB credentials, key config
docker compose up
```

Verify the server is running:

```bash
curl http://localhost:9000/.well-known/smart-configuration | jq .
```

You should see `authorization_endpoint`, `token_endpoint`, `scopes_supported`, and `capabilities` (including `launch-ehr`, `launch-standalone`, `client-public`, `sso-openid-connect`).

The reference SMART client is at `http://localhost:8081`. For a standalone launch, visit `http://localhost:8081/launch` and pick a patient.

## Configuration

### Auth Server (`smart-auth-server`)

| Env Var | Default | Description |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/smartfhir` | PostgreSQL JDBC URL |
| `DB_USER` | `smartfhir` | Database username |
| `DB_PASSWORD` | `changeme` | Database password — change in production |
| `FHIR_BASE_URL` | `http://localhost:8080/fhir` | HAPI FHIR base URL |
| `ISSUER_URL` | `http://localhost:9000` | Public OAuth2 issuer URL (appears in `iss` claim) |
| `ACCESS_TOKEN_TTL` | `3600` (dev) / `300` (prod) | Access token lifetime in seconds |
| `KEYSTORE_PATH` | — | Path to `.p12` keystore (required in prod profile) |
| `KEYSTORE_PASSWORD` | — | Keystore password |
| `ADMIN_USERNAME` | `admin` | Bootstrap admin username |
| `ADMIN_PASSWORD` | `changeme` | Bootstrap admin password — change immediately |

### SMART Client (`smart-client`)

| Env Var | Default | Description |
|---|---|---|
| `FHIR_BASE_URL` | `http://localhost:8080/fhir` | FHIR server base URL |
| `AUTH_SERVER_URL` | `http://localhost:9000` | Auth server base URL |
| `CLIENT_ID` | `smart-client` | OAuth2 client ID |
| `CLIENT_SECRET` | `changeme` | OAuth2 client secret (confidential client) |
| `REDIRECT_URI` | `http://localhost:8081/callback` | OAuth2 callback URL |

### Profiles

| Profile | Use | Notes |
|---|---|---|
| `dev` | Local development | H2 in-memory, generated RSA key, seed data loaded, no cleanup job |
| `prod` | Production | PostgreSQL + Flyway, keystore required, cleanup job active |
| `prod,idp` | Production + federated IdP | All of prod plus upstream OIDC IdP delegation |

## Architecture

```
Browser / EHR
     │
     │  ?iss=http://localhost:8080/fhir&launch=<token>
     ▼
SMART Client (:8081)
  SmartLaunchController       ← receives EHR launch parameters
  SmartCallbackController     ← handles OAuth2 callback + PKCE token exchange
  IdTokenValidator             ← RS256 JWT verification via JWKS
  TokenRefreshFilter           ← transparent background token refresh
  PatientDataController        ← FHIR API calls with scoped bearer token
     │
     │  GET /oauth2/authorize?response_type=code&code_challenge=...
     ▼
Auth Server (:9000)
  AuthorizationServerConfig    ← Spring Authorization Server, PKCE, CORS
  ConsentController            ← scope consent page (Thymeleaf)
  SmartTokenCustomizer         ← injects patient/encounter into JWT claims
  SmartTokenResponseConverter  ← promotes SMART claims to token response body
  LaunchContextService         ← creates + validates single-use launch tokens
  LaunchPortalController       ← clinician login + patient picker UI
  SmartDiscoveryController     ← /.well-known/smart-configuration
  SmartScopeAuthorizationInterceptor  ← enforces SMART scope on FHIR requests
     │
     │  FHIR API + introspection
     ▼
HAPI FHIR JPA (:8080)         ← your server; configure introspection endpoint
```

## Roadmap

This project is actively developed. Contributions are welcome.

### v0.3 — Hardening & operations

- [ ] `SmartDiscoveryProxyFilter` response cache (Caffeine TTL=60s) for high-traffic deployments
- [ ] Remove `DataInitializer.seedImmunizationApp()` dead method
- [ ] Login lockout state backed by Redis/PostgreSQL for multi-instance deployments (current: Caffeine in-memory, single instance only)
- [ ] Rate-limit state backed by Redis for multi-instance deployments
- [ ] Helm chart for Kubernetes deployment
- [ ] Production Docker image with non-root user, health probe, graceful shutdown

### v0.4 — SMART on FHIR feature completeness

- [ ] **Backend services** (SMART App Launch v2.2 §9) — client credentials flow with signed JWT assertion; no user interaction required; for system-to-system FHIR access
- [ ] **Token revocation** (RFC 7009) — `POST /oauth2/revoke` endpoint (stub present; enforcement in FHIR interceptor not yet wired)
- [ ] **App-level access policies** — per-registered-app allowed scope ceiling; admin can restrict an app to `patient/*.rs` even if it requests broader scopes
- [ ] **Audit log** — structured `AuditEvent` FHIR resources written to HAPI FHIR on every token issue and FHIR API access; required for HIPAA compliance
- [ ] **Patient-facing consent management** — patients can view and revoke app authorisations from a self-service portal

### v0.5 — Multi-tenant & federation

- [ ] **Multi-tenant mode** — single deployment serves multiple FHIR servers; tenant resolved from ISS; separate key material and app registries per tenant
- [ ] **Dynamic client registration** (RFC 7591) — apps self-register; admin approval workflow
- [ ] **UDAP** (Unified Data Access Profiles) — trust community federation; signed software statements for B2B FHIR access
- [ ] **CDS Hooks integration** — launch SMART apps from CDS Hooks cards; pass hook context into launch token

### v1.0 — Certification target

- [ ] **ONC g(10) certification alignment** — scope set, capability declaration, and id_token claims aligned with US Core SMART requirements
- [ ] **SMART Health Cards / SHL** — verifiable clinical data export (COVID vaccination, insurance)
- [ ] **Inferno test suite** pass — [HL7 Inferno SMART App Launch test suite](https://inferno.healthit.gov/) full green
